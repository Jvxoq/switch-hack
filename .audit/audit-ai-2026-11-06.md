## Findings

### 1. [Fatal] Nobody owns incident state after the alert
Evidence: `tasks.md:265` E01 keeps incidents in the detector (`state.json`). `tasks.md:106` the
`ContainmentClient` port can `apply`, `revert` and read `flags()`, but cannot report which incident got
which action, from whom. `tasks.md:306` A01 gives Tripwire only `langfuse_read`, `flags_read`,
`request_containment`: no tool reads or writes incident state. `tasks.md:284` E03 only resolves incidents
already in `contained`.
Why it hurts: nothing ever moves an incident to `investigating`, `awaiting_approval`, `contained` or
`handed_off`, and nothing fills `approver`, `approved_at`, `root_cause`, `pr_url` or `rejections`
(`tasks.md:98`). So after Allow once, E03 never resolves (T20 fails), E02 cannot tell an approved incident
from an unapproved one (`tasks.md:276`), E01 cannot know which incident is being investigated to mark
others `queued` (`tasks.md:267`), and the incident record (T18) is mostly `—`. Each unit test still passes,
because each one sets the state by hand on fakes.
Fix: make the containment service the single incident store. Add `GET /incidents/{id}` and
`PATCH /incidents/{id}` (state, root_cause, pr_url, approver, rejections) to the contract in C01, have
`POST /actions` set `contained`/`auto_paused`, have the detector read incidents from the service each poll,
and give Tripwire an `update_incident` tool in A01.

### 2. [Serious] The detector only sees traces started since the last poll
Evidence: `tasks.md:104` `recent_traces(since)`; `tasks.md:292` E04 fetches "since last poll − overlap".
L01 filters on `fromTimestamp` (`tasks.md:228`), which is the trace start time. R03 needs one hour of
traces for its median (`tasks.md:211`), R02 a 5-minute window (`tasks.md:205`), E02 one hour of route
spend (`tasks.md:277`).
Why it hurts: a looping trace that started before the last poll is never fetched again, which breaks
decision #2 (judge running traces, `tripwire-product-proposal.md:196`). The cost and silent-error rules get
15 seconds of data instead of an hour or 5 minutes, so they almost never fire live. Unit tests hide this
because fixtures hand each rule a full window.
Fix: in E04, keep a rolling one-hour cache of traces by ID, re-fetch every still-running trace by ID each
poll, and pass the whole cache to every rule. Add one E04 test where a trace starts before the poll and
crosses the threshold after it.

### 3. [Serious] "One action per incident, forever" blocks two flows the proposal promises
Evidence: `tasks.md:219` S01: "at most one applied action (revert does not free a second one)".
`tasks.md:285` E03: a new hit during verification goes back to `awaiting_approval` and re-asks.
`tripwire-product-proposal.md:207` decision #13: after auto-pause "other actions still wait".
Why it hurts: after a reopen, the re-asked action is refused by the service. After an auto-pause, the
owner's approved `cap_max_steps` or `fallback_model` is refused too. The approval button works, then nothing happens.
Fix: change the rule to "at most one *active* action per incident". A new action is accepted only after
the previous one is reverted, or when it replaces an auto-pause. Add both cases to T10.

### 4. [Serious] Tripwire's 20-call / 3-minute cap lives only in the prompt
Evidence: `tasks.md:312` puts the guard in `instructions.md`. No tool or server counts calls.
Why it hurts: this is a known repeat mistake: a limit the model is asked to keep is not a limit. The
agent built to stop runaway agents can itself run on, and T16 would measure if Claude obeys, not if the
system stops it.
Fix: enforce it in A01's tool server: a per-incident call counter and deadline. After either one, every
tool returns "budget spent, post partial findings", and the server sets `handed_off`.

### 5. [Serious] The three agent evals can be skipped and still count as done
Evidence: `tasks.md:330` evals skip without `ANTHROPIC_API_KEY`. `tasks.md:365` X01 only checks that a test
named T1–T20 *exists*. `tasks.md:329` allows running "the Claude API with the same instructions" instead
of Claude Code. Each eval has one recorded incident.
Why it hurts: the proposal is done only when every behavior has a *passing* test
(`tripwire-product-proposal.md:12`). A skipped T13/T16/T19 is not passing. A single sample of a model
call passes or fails by chance, and an API harness is not the Claude Code agent that runs in Switch.
Fix: X01 must run `pytest -m eval` with a key against Claude Code headless, at least 5 runs per eval
fixture, and write the pass counts to `docs/test-matrix.md`. Skipped counts as failed.

### 6. [Serious] Switch unknowns sit on the critical path with no fallback
Evidence: C01 freezes `SwitchPoster.update_header` (`tasks.md:105`) before C02 researches whether an
external process can post or edit in a thread (`tasks.md:185`). C02 may answer `UNKNOWN`
(`tasks.md:189`). The human Switch setup H01 waits for A01 (`tasks.md:155`, wave 5 at `tasks.md:159`).
The deadline is Nov 7, 11:59 PM IST (`tasks.md:10`).
Why it hurts: if Switch cannot edit a header, or a non-Claude process cannot post as an agent, W01, E01,
A01 and H02 all rework late. Discovering that on the last day, at wave 5, kills the demo.
Fix: start with a spike before C01 freezes contracts. The human installs Switch, creates the room and
posts one message from a script as `tripwire-detector`. C02 records what worked, and the
`SwitchPoster` port is written to match it (for example, a new status reply instead of a header edit).

### 7. [Serious] `revert INC-<n>` has no handler
Evidence: decision #15 says an owner runs `revert INC-12` in the room (`tripwire-product-proposal.md:209`).
E02 replies offering it (`tasks.md:276`). S01 builds `POST /revert` (`tasks.md:116`), but A01's tool list
(`tasks.md:306`) has no revert tool, and no task parses the command.
Why it hurts: the only undo path is a curl command. Auto-pause is "safe" in the pitch because a person can
undo it in chat.
Fix: add an owner-only `revert_containment` tool to A01, and one E2E step in H02 that reverts.

### 8. [Worth fixing] "Resolved" after disable_route proves nothing
Evidence: `tasks.md:284` E03: `contained`/`auto_paused` plus 5 quiet minutes means `resolved`.
Why it hurts: a disabled route makes no traces, so it is always quiet. The incident shows Resolved while
production is still switched off, and nobody is told to turn it back on.
Fix: for `disable_route`, stay `contained` until an owner reverts, then start the 5-minute check.

### 9. [Worth fixing] The loop rule does not catch the loop the pitch leads with
Evidence: the proposal's first failure is "the agent rephrases the same tool call"
(`tripwire-product-proposal.md:21`). R01 treats inputs as the same only when they are equal after
lowercase, whitespace and key sorting (`tasks.md:197`).
Why it hurts: a rephrased query only trips the 25-observation fallback. A judge who reads the problem
table and then sees an exact-match rule notices this.
Fix: make D01's loop bug repeat a structured call (same `order_id`), and say in the README that rephrased
loops are caught only by the observation cap in the MVP.

### 10. [Worth fixing] The service takes the caller's word on spend
Evidence: `tasks.md:115` `POST /actions` takes `evidence: {spend_usd, opened_at}` from the caller.
`tasks.md:220` says checked "against the service's own config + clock", which covers time, not spend.
Why it hurts: decision #21 says auto-pause only when the condition is "truly met"
(`tripwire-product-proposal.md:215`). Any caller that can reach `:8700` can claim $25 and pause a route.
Fix: use `opened_at` from the service's own `/incidents` record, ignore the caller's copy, and write in
the contract that spend is trusted from the detector only. Bind the service to the Compose network.
